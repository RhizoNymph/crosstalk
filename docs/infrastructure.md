# Infrastructure

Where crosstalk's data lives, how it runs, how it is deployed and how it
scales. The current target is the simplest slice that works: one machine,
docker compose, 100–200 live agents. Each choice below names the seam that
later replaces it, so the bigger deployments are swaps behind existing
traits rather than rewrites.

The deployment files are in `deploy/`; `docs/features/deploy.md` documents
them and the contract the `crosstalk` binary implements for them.

## Decisions

| Area | Now | Later (the seam) |
|---|---|---|
| Deployment | docker compose on one machine (`deploy/compose.yaml`) | Same images split by role; Kubernetes only if multi-node needs it |
| Process shape | One `crosstalk` binary, `serve --role all` | `--role proxy\|pipeline\|api\|analysis` on separate containers |
| Bus | In-process `MpscBus` | NATS JetStream adapter behind `EventBus` (P9) |
| Structured state | Postgres 18 + pgvector + pg_trgm, one schema per layer | Read replica for `api`; hash-partitioned fingerprints |
| Time series (D3) | Plain Postgres, no TimescaleDB | Native range partitions on time-bucketed tables |
| Bodies | `FsBlobStore` on the `data` named volume (`/var/lib/crosstalk/blobs`) | S3-compatible store behind `BlobStore` |
| Body retention | Per-message blobs kept indefinitely (issue #38); raw request bodies are never stored | Retention jobs dropping old message blobs |
| Embeddings | A hosted OpenAI-compatible endpoint, so embedding never waits on a slow local model: OpenAI `text-embedding-3-small` in `deploy/config/crosstalk.json`'s `embeddings` block, keyed by `CROSSTALK_EMBEDDINGS_API_KEY` in `deploy/.env`. Another hosted provider is a `base_url` and `model` change | A local model on the deployment host's GPU, behind the same config block; scaling hosted compute is the provider's problem, not ours |
| Topics / UMAP (D1) | Behind the L6 traits; batch, not streaming | A Python batch worker (umap-learn, HDBSCAN) if Rust options fall short |
| API server (D5) | axum (on the workspace's hyper 1.11.1) | — |
| Infra observability | Prometheus, Grafana, Loki, Alloy, node-exporter, cAdvisor, postgres-exporter | Same stack; app metrics join on the ops port |
| Backups | None | WAL-G or pgBackRest to object storage; bucket versioning for blobs |
| Enforcement | Observe only | Deny unsanctioned channels at the proxy (below) |

## Where things are stored

**Postgres** holds every structured record: agents, threads, fingerprints,
matches, resources, channels, transmissions, verdicts, alerts, the audit log,
edge buckets, embeddings (pgvector) and search (pg_trgm). Each layer owns a
schema and its own migrations table (`crates/store`). Without TimescaleDB,
the tables that grow with time (exchanges, transmissions, L7 buckets) are
the candidates for native range partitioning when retention arrives;
dropping a partition is then the retention job. L7 already pre-aggregates
into buckets, so continuous aggregates would add little.

**Blobs** are content-addressed by BLAKE3 in `FsBlobStore`, under
`/var/lib/crosstalk/blobs` on the `data` named volume. L1 (`crates/canonical/src/capture.rs`) stores each canonical
*message* as its own blob keyed by its hash, not each request body. Agent
harnesses resend the whole conversation every turn, so this is what keeps
storage linear: the repeated prefix of a conversation is the same set of
message hashes, and only the new turn costs bytes. Raw request bodies are
not kept; per-message content is enough.

Cheap later wins: zstd-compress blob files (tool output compresses 3–5×),
and store embeddings as `halfvec` to halve their size.

**Secrets** are in `deploy/.env` (git-ignored, generated by `run.sh init`).
Config files name the environment variable that holds each secret
(`{"env": "CROSSTALK_SECRET_V1"}`), never the secret itself.

## How it runs

One binary, one process, every role, as the compose service `crosstalk`:

```
agents ──HTTP──▶ :8080 proxy (L0) ──▶ upstream APIs
                    │ capture tee (never slows the client)
                    ▼
               in-process bus ──▶ L1 … L7 consumers ──▶ Postgres, blobs
                                                          ▲
operator UI ──▶ :8081 API (L8, SSE) ─────────────────────┘
Prometheus ──▶ :9464 ops (/metrics, /healthz, /readyz)
```

The roles the binary will split into later:

| Role | Contains | State | Scales by |
|---|---|---|---|
| `proxy` | L0 | none (local spool later) | replicas behind a load balancer |
| `pipeline` | L1–L7 consumers | Postgres, blobs | JetStream consumers sharded by key |
| `api` | L8 (QueryApi, SSE, export) | reads Postgres | replicas + a read replica |
| `analysis` | topics, projections, rule batches | Postgres | scheduled jobs |
| `all` | everything, in-process bus | | one machine |

The proxy is on every agent's critical path, so it must never wait on the
database or the bus to forward: capture is a bounded tee, and a full capture
channel costs that exchange's capture, not the agent's request.

## Sizing for 100–200 agents

LLM calls are slow, so request rate is small; bytes and the database are
what grow.

- **Traffic.** 200 agents at one call every 10–20 s is 10–20 requests/s with
  up to ~200 concurrent streams (each stream holds a client and an upstream
  socket; `nofile` is raised to 65536).
- **Memory in the proxy.** Request tees are bounded at 32 MiB each, but
  typical bodies are 100 KB–1 MB: roughly 200 MB at 200 concurrent exchanges.
- **Blob growth.** After per-message dedup, each call adds the new turn and
  its tool results, about 10–30 KB. At a sustained 20 requests/s that is
  ~0.4 MB/s, or ~35 GB/day; a two-hour demo with 200 agents is a few GB.
- **Postgres.** The same order as blobs (fingerprints dominate), plus
  ~3 KB per embedded message at 1536 dimensions (half that as `halfvec`).
- **Machine.** 8 vCPU, 16–32 GB RAM, 200 GB+ NVMe is comfortable. The
  compose defaults (`shared_buffers=2GB`, `effective_cache_size=6GB`,
  `max_connections=200`, a pool of 40) assume 16 GB; raise them in
  `deploy/.env` on a bigger box.

## Deployment

`deploy/compose.yaml`, project name `crosstalk`:

- `postgres` (pgvector 0.8.6, Postgres 18) with `pg_stat_statements`
  preloaded and a read-only `crosstalk_monitor` role for the exporter.
- `migrate` runs `crosstalk migrate` once, then exits; `crosstalk` starts
  only after it succeeds. Upgrades are therefore: build, `up -d` (migrate
  runs first), and the strict wire contract is safe because the in-process
  bus never holds messages across a restart.
- `crosstalk` (`serve --role all`), healthy when `/readyz` answers.
- `ui` (profile `ui`, added by `run.sh` whenever `ui/` exists): the operator
  UI on its HTTP backend, reading the gateway's API at `crosstalk:8081` with
  `CROSSTALK_API_TOKEN`; it starts once `crosstalk` is healthy.
- The observability stack (below).

Only the proxy binds beyond localhost; the API, UI, Grafana, Prometheus and
Postgres bind 127.0.0.1 (reach them over SSH forwarding, or change the bind).
node-exporter runs on the host network on port 19100. Every published host
port is a `deploy/.env` variable, so the stack fits beside other projects
on a shared machine; `docs/features/deploy.md` ("Running on a shared host")
covers snap Docker, port clashes, syncing a checkout and a smoke test.

### Accepted risks

Accepted for now, for the hackathon, each with what replaces it:

| Risk | Now | What changes it |
|---|---|---|
| Plain HTTP on the proxy | Agents' requests, credentials included, cross the network unencrypted; the proxy belongs on a trusted network | A TLS terminator in front of the proxy |
| Unbounded disk growth | Bodies are kept (issue #38) and nothing deletes blobs or rows; see the growth figures under sizing | Retention jobs: dropping time partitions in Postgres and unreferenced blobs |
| No backups | Losing the host's disk loses Postgres and the blobs | WAL-G (or pgBackRest) to object storage, and bucket versioning once blobs move to S3 |

## Demo and load testing

`deploy/compose.demo.yaml` layers a token-free demo over the stack. A fake
Anthropic upstream (`fake-upstream`) answers deterministically, with
realistic first-byte waits and 1–10 s streams. A shared in-memory wiki
(`wiki`) is the channel. A swarm of simulated agents (`swarm`, profile
`swarm`, never restarted) drives 100–200 concurrent conversations through
`crosstalk:8080`. Its agents write wiki pages with the model's words and
read each other's pages back as tool results. The gateway reads
`deploy/demo/crosstalk.demo.json`, which points the Anthropic route at the
fake upstream. `bash deploy/run.sh demo up`, then `demo run [--agents N
...]`, prints throughput, client-observed latency percentiles and the
expected cross-agent transmissions. Watch the stack in the usual Grafana
dashboards meanwhile. `demo down` stops it. Details and knobs:
`docs/features/demo.md`.

## Observability (infrastructure)

| Signal | Source | Where |
|---|---|---|
| Host CPU, memory, disk, network | node-exporter (host network) | Grafana "crosstalk / infrastructure" |
| Per-service CPU, memory, restarts, IO | cAdvisor, labelled by compose service | same |
| Postgres connections, TPS, cache hits, size, slow statements | postgres-exporter + `pg_stat_statements` | same |
| Every container's logs | Alloy → Loki (7 days), `level` lifted from JSON logs | Grafana Explore / logs row |
| Alerts | Prometheus rules (`deploy/prometheus/rules/`) | Prometheus and Grafana UIs (no Alertmanager) |
| The gateway itself | `crosstalk:9464/metrics` (capture, pipeline and exchange log counters, draining) and its WARN/ERROR logs | Grafana "crosstalk / gateway"; alerts in `deploy/prometheus/rules/gateway.yml` |

Application metrics (proxy added latency, capture drops, bus queue depth,
L7 watermark lag, embedding queue) belong to the application and arrive on
the ops port; the scrape job and the dashboard's "crosstalk process" row are
already there for them.

## Scaling path

1. **One box (now).** Everything above.
2. **Split roles.** Stateless `proxy` replicas behind a load balancer, one
   `pipeline`, a separate `api`; NATS JetStream replaces the in-process bus;
   the S3-compatible blob store replaces the volume; a Postgres read replica
   serves `api`. Put the wire version in JetStream stream names so a new
   version consumes a fresh stream while the old pipeline drains the old
   one: strict decoding then loses nothing across an upgrade.
3. **Shard the pipeline.** JetStream subjects partitioned by key (L3 ordered
   per agent, L4 by fingerprint hash); fingerprint table hash-partitioned.
   Embedding throughput is the embedding provider's to scale.

## Enforcement: denying unsanctioned channels (stretch)

Goal: once an operator marks a channel unsanctioned, agents stop receiving
content through it.

**Where to cut.** The model never sees a channel directly; it sees a
`tool_result` in its next request (the harness ran the tool locally). The
proxy cannot stop the harness from running a tool, and it cannot hold back
a streamed response without breaking streaming. It can rewrite the next
request: replace the `tool_result` content of any tool call that targets a
denied resource with a fixed notice ("blocked by crosstalk policy: channel
<name> is unsanctioned") and forward the rest. The agent keeps working, the
content never reaches the model, and because the rewrite is deterministic
the harness's resent history rewrites identically each turn (prompt caching
still sees a stable prefix).

**Shape.**

- A spec trait, e.g. `RequestPolicy`, that ingress calls before forwarding
  on routes with enforcement enabled. Ingress cannot depend on L5, so the
  gateway composes: L5 (which already resolves tool calls to resources)
  implements the matcher, compiled into a deny-set of resource keys.
- The policy snapshot reaches the proxy through a `tokio::sync::watch`
  channel when channel verdicts change; the hot path never queries Postgres.
- Only the newest messages need checking (the last user turn's
  `tool_result`s and the `tool_use`s they answer); older turns were checked
  when they were new, and their rewrite is replayed from the snapshot.
- Bounded time budget; on a parse failure or timeout, forward unmodified and
  count it (fail open), unless a route is configured fail-closed.
- Each block emits a `TransmissionBlocked` event: an audit entry, an alert,
  and a mark on the channel's edge in the topology.

**What it changes in the spec.** The ingress invariants say the proxy
forwards before it decodes. Enforcement is a deliberate, bounded exception
for enforcing routes only, and needs new invariants for: the rewrite
touching only denied `tool_result`s, determinism of the rewrite, the time
budget and fail-open behaviour, and the audit trail.

**When.** After the capture → pipeline → UI path demos end to end. A crude
version (static deny-list of resource keys in config, rewrite, log) is a
couple of hours on top of a working pipeline; the verdict-driven version
follows from it.
